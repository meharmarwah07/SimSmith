# SimSmith demo UI

A local, stdlib-only web UI for the SimSmith pipeline. Dark theme, works at
laptop and phone widths, no CDN/npm/pip deps.

Every run result carries a `source` field (`mock` | `live` | `recorded_live`)
and the page shows an unmissable badge for it -- "MOCK: scripted LLM, no
model was called" for a mock run or a recording of one, "Recorded live run:
\<model\>, \<date\>, prompt \<version\>" for a labeled recorded-live fixture.
A `--replay` fixture with no `source` field is refused at startup rather than
served without a badge.

## Run it

```
python -m app.server --mock --port 8000
```

Then open http://127.0.0.1:8000/. `--mock` builds the pipeline from
`tests/mocks.py` (a scripted LLM + the real `mujoco` already installed here),
so a run needs no network access and no API key. Type a task or click one of
the three example chips, then press **Run**. A single run takes ~5-10s and
exercises the whole pipeline: 5 candidates (one verified immediately, one
crashes, one is rejected by pre-flight for a banned import, one is rejected
for never stepping physics, one is wrong and gets repaired), a repair round,
and a winner.

### Replay mode (for the demo video)

```
python -m app.server --replay app/fixtures/sample_run_MOCK.json --port 8000
```

Serves one pre-recorded run with **no** LLM or sim calls at all -- the page
loads already showing a finished VERIFIED run, tagged with the "MOCK" badge
since that's what `source` says in the fixture. `/api/run` returns 409 in
this mode (read-only), so there's nothing that can fail on camera. The
fixture was generated by running `--mock` once and saving
`serialize_result()`'s output; regenerate it the same way if you want a
different recorded run. The filename ends in `_MOCK` as a second,
filesystem-level reminder of what it is, on top of the `source` field inside
it. A genuinely recorded live run would be saved the same way but with
`source: "recorded_live"` (set that by hand, or once the pipeline supports
recording a real run, by the server) -- `build_state()` refuses to start in
`--replay` mode for any fixture missing `source` altogether.

### Live mode (real Token Factory + real sim)

```
python -m app.server --port 8000
```

Builds the pipeline from `Config.from_env()`, exactly like
`scripts/gate_day1.py` -- needs `TOKEN_FACTORY_BASE_URL` / `TOKEN_FACTORY_API_KEY`
(and ideally `SIMSMITH_SIM_PYTHON`) set via `.env` or the environment. Fails
fast with a clear message if those aren't set, rather than silently falling
back to mock behavior.

All three modes bind to `127.0.0.1` only.

### Eval results page

```
python -m app.server --mock --results-dir eval/results --port 8000
```

`/results` reads whatever `*.json` files are sitting in `--results-dir`
(default `eval/results/`) and renders a model x condition table: pass rate
with a Wilson 95% interval, n, mean seconds, mean cost, a failure-mode bar,
and the prompt version/model/date for each file. It tolerates two shapes
that already exist in this repo -- `eval/run_eval.py`'s condition-keyed
output and `scripts/baseline_dev.py`'s template-keyed output with a
precomputed failure breakdown -- and reports (without crashing) any file
that matches neither. A caption on the page says plainly: "n is small on
dev tasks; intervals are wide."

### Backend comparison panel

The main page also shows a "Backend comparison (speed, coverage, stability)"
panel, fed from `app/fixtures/backend_comparison.json`. Only MuJoCo (the
backend this demo actually runs) is marked `measured`; everything else is
explicitly `not measured`. The panel carries a visible "Real-world fidelity
not tested" note and never ranks backends or calls one "best".

### Media slot

If the winning candidate's JSON has a `clip_path` (not emitted by the
pipeline today -- read defensively via `getattr`, so this activates the
moment a future pipeline starts recording clips with no change needed here),
the Winner section shows a gif/png image or an mp4/webm video player for it;
otherwise it shows "no recording". Clips are served from `--media-dir`
(default `app/media/`) through `GET /api/media?path=...`, which only ever
serves files under that one directory (checked against the *resolved* path,
not the string, so `..` segments and symlink tricks are both rejected) and
only for a small allow-listed set of extensions.

## Run the tests

```
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python3 -m pytest tests/test_app.py -q
```

(`PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` works around a broken `anyio` pytest
plugin in this environment, unrelated to this change -- the same workaround
is needed for `tests/test_core.py`.) 33 tests, all against a real
`ThreadingHTTPServer` over a real socket:

- **Core run flow (unchanged):** end-to-end run + status polling, the
  gap-statement path for a non-exact task, 409 while busy, 413 for an
  oversized body, 400 for a missing/blank task, replay loading and its
  read-only `/api/run`.
- **XSS safety (unchanged):** a `<script>` tag embedded in a candidate's
  generated code can never execute -- the client code contains no
  `innerHTML`/`outerHTML`/`insertAdjacentHTML`/`document.write` sink at all
  (checked by reading `app.js`), and the payload really does reach the API
  as raw text, so that guarantee isn't vacuous.
- **Integrity badge:** a mock run's own JSON always carries `source: "mock"`;
  `build_state()` refuses (`sys.exit(1)`) to serve a `--replay` fixture
  missing `source` at all; `app.js`'s `renderResult()` is checked
  structurally to call `renderSourceBadge()` unconditionally and to contain
  both required badge strings.
- **Results page:** `/api/results` against a temp dir containing a
  hand-built `eval/run_eval.py`-shaped file and a `scripts/baseline_dev.py`-
  shaped file, checking the Wilson interval against `wilson_interval()`
  directly, condition-name mapping (`best_of_5` -> `best_of_5+repair`), and
  that a malformed/unrelated file is reported in `errors` without taking
  down the other rows.
- **Backend comparison:** the endpoint matches the fixture, the fixture (and
  the page) never claims a "best"/"recommended" backend, and the fidelity
  note is present.
- **Media slot:** a real file under `app/media/` is served with the right
  content type and bytes; three different `../` traversal encodings and an
  absolute path are all rejected; `_safe_media_path()` is also tested
  directly; `serialize_candidate()` surfaces `clip_path` when present on the
  candidate object and reports `None` when absent.
- **Polish:** copy-to-clipboard and the exact failure-state wording are
  checked structurally in `app.js`; the mobile `@media` rule covers the new
  elements; every clickable control is a real `<button>`/`<a>`.

## API

- `POST /api/run {"task": "..."}` -- starts a run in a background thread.
  `202` once started, `409` if a run is already in progress or the server is
  in `--replay` mode, `400` for a missing/blank task, `413` for a body over
  10 KB.
- `GET /api/status` -- `{mode, state, busy, task, result, error, library_size}`.
  `state` is `idle | running | done | error`. `result` (once done) is the
  full serialized run: template + gap, all 5 candidate slots (each with its
  attempt history across repairs), per-seed pass/fail/crash with detail text,
  repair rounds, the winner (or `null` with the closest template + gap if
  nothing verified), the seconds/tokens/dollars/sim-runs/library-size
  counters, and the integrity fields `source` / `model` / `prompt_version` /
  `date`.
- `GET /api/replay` -- the recording loaded via `--replay`, or 404 if the
  server wasn't started with one.
- `GET /api/results` -- `{results_dir, rows, errors}` for the `/results`
  page; see "Eval results page" above.
- `GET /api/backend-comparison` -- the contents of
  `app/fixtures/backend_comparison.json`.
- `GET /api/media?path=...` -- serves one clip from `--media-dir`; `400` for
  an unsupported extension, `404` for anything outside the directory or that
  doesn't exist.

The API key, base URL, and other env vars are never read by the handler and
never appear in any response -- `serialize_result()` only ever emits the
small set of fields listed above.

## What to add after merge

- **Progress events.** Right now a run shows nothing until it finishes
  (`Pipeline.solve()` is one blocking call -- see the comment in
  `app/server.py::run_task`). The lowest-risk way to add live progress
  without touching `simsmith/pipeline.py` is a server-layer wrapper that
  calls the pipeline's already-public stage methods (`intake`, `plan`,
  `generate`, `evaluate`, `repair`) itself instead of `solve()`, updating a
  shared "stage" field between calls that `/api/status` can report while
  `state == "running"`. This was deliberately **not** done here: it would
  mean re-implementing `solve()`'s orchestration logic in `app/`, and
  `simsmith/pipeline.py` is being actively edited in another session right
  now -- a duplicate copy would silently drift the moment that method
  changes. Once that other work lands, either add a real progress-callback
  parameter to `Pipeline.solve()` (cleanest) or do the wrapper above.
- **Perturbation / robustness runs.** The runner already threads
  `SIMSMITH_PERTURB` through (`simsmith/runner.py`); once stage 7b exists,
  surface it as an optional toggle before Run and show the perturbed seeds
  alongside the normal ones.
- **Multiple saved recordings.** `--replay` takes one file; a `--replay-dir`
  that lists several fixtures with a picker would let the demo video jump
  between a clean VERIFIED run and a FAILED/gap-only one without restarting
  the server.
- **Cross-run history.** `/api/status` only ever holds the latest run.
  Keeping the last N results in memory (or reading `eval/results/*.json`)
  would let the page show a trend instead of a single snapshot.
