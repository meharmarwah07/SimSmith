## World-frame conventions

- World frame is the scene's root frame (body `world`, id 0); all positions below are in this frame, metres, right-handed, **z-up** (gravity is [0.0, 0.0, -9.81] m/s^2, i.e. -z).
- The robot base (body `link0`) sits at the world origin (pos=[0.0, 0.0, 0.0], no rotation) -- world coordinates ARE base coordinates for this robot.
- The ground/table surface is the `floor` plane geom at world z=0 (`<geom name="floor" type="plane" .../>` in the included scene file). There is no separate table body/geom; the floor plane is the support surface the cube and the robot rest on.

### `cube_free` layout (free joint)

- `qpos[9:16]` = `[x, y, z, qw, qx, qy, qz]` -- **position (3) then quaternion (4, scalar-first `wxyz`)**. This is the cube body's pose relative to its parent (`cube` body's own `pos` is `0 0 0` in its XML, so this IS the cube's world pose).
- `qvel[9:15]` = `[vx, vy, vz, wx, wy, wz]` -- linear velocity (3) then angular velocity (3), both in the world frame for a free joint.
- `cube_initial_pos` from `get_task("pick_place")` is where a script must WRITE this joint's position qpos entries (quaternion left as the scene's default, identity `1 0 0 0`, unless the task perturbs orientation) before stepping physics forward; nothing sets this automatically.
- `write_result()` measures `cube_velocity` as this joint's 3 linear qvel entries (not angular) from the last-step snapshot.

## Where get_task() values apply

- `get_task("pick_place")["cube_initial_pos"]` is where the script must set the EXISTING `cube` body's free-joint position (see `cube_free` layout above) before stepping physics -- the cube is already in the scene XML at a fixed placeholder pose (`0.5 0 0.02`); a script must override that with this run's sampled value, not add a new body.
- `get_task("pick_place")["bin_center"]` is a free-standing world-frame point with **no physical representation at all** -- no body, no geom, no collision volume, nothing the cube can rest in or collide with. The success check (`simsmith/templates.py`, not reproduced here) compares final `cube_pos` against this point and against `cube_initial_pos`/`cube_velocity`/`gripper_opening`; a script does not need to, and cannot, place the cube "inside" anything physical.
